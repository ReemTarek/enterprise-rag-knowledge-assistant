# Security

Describes behaviour as implemented at the end of Phase 2a. See ADR 0004 for the rationale.

## Authentication

- **Users**: domain-owned `User` (email, display name, password hash, global role, active flag, lockout state).
  Accounts are created by the seeded admin or by admins (`POST /api/admin/users`); there is no self-registration.
- **Password hashing**: ASP.NET Core Identity `PasswordHasher<T>` (PBKDF2 V3, HMAC-SHA512, random salt) behind the
  Application port `IPasswordHasher`. Nothing else from Identity is used.
- **Password policy** (`Security:MinPasswordLength`, default 12, range 8-128): minimum length, at most 128 characters,
  at least one upper-case letter, one lower-case letter and one digit. A changed password must differ from the current
  one. The 128 maximum also bounds every password input before any hashing: a longer current/new password on
  `POST /api/auth/password` is a 400 validation error, a longer login password is the generic 401 without a database
  lookup, hash or lockout count, and a longer `Seed:AdminPassword` fails startup.
- **Temporary passwords**: generated by a CSPRNG (>= 20 chars, upper/lower/digit/symbol, no look-alike characters).
  Returned once in the create/reset response (`Cache-Control: no-store`), stored only as a hash, never logged. A user
  holding one has `mustChangePassword = true`. The seeded admin also starts with `mustChangePassword = true`.
  The flag is enforced server-side (see "Must-change-password enforcement" below).
- **Access token**: JWT, HS256, 15 minutes (`Jwt:AccessTokenMinutes`), claims `sub`, `role`, `jti`. Validated for
  issuer, audience, signature, lifetime (30 s clock skew) and algorithm (HS256 only). The signing key is at least 32
  UTF-8 bytes, has no default and must come from environment/user-secrets (startup fails otherwise).
- **Refresh token**: opaque, 64 random bytes (base64url), 7 days (`Jwt:RefreshTokenDays`). Only its SHA-256 hash is
  stored. Delivered only as the cookie `refresh_token`: `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`. It is
  never in a response body and a token in a request body is ignored.
- **Rotation and reuse detection**: every refresh revokes the presented token and issues a new one in the same family.
  Presenting an already revoked token revokes the whole family (treated as theft) and returns the generic 401. A
  concurrent rotation of the same token (row-version race) is handled the same way.
- **Logout**: `POST /api/auth/logout` is anonymous - the refresh cookie is the credential, so a client whose access
  token has expired can still sign out. It revokes the token's family, always clears the cookie and succeeds silently
  for unknown/missing cookies. The Angular client clears its in-memory session first and sends this call best effort
  (5 s timeout); if it never reaches the server the cookie stays valid until expiry (see `docs/FRONTEND.md`).
- **Lockout**: 5 consecutive wrong passwords (`Security:MaxFailedLogins`) lock the account for 15 minutes
  (`Security:LockoutMinutes`). Attempts during a lockout neither extend it nor count towards the next. Unknown,
  inactive and locked accounts burn one dummy hash verification and return the same generic 401 ("Invalid
  credentials.") as a wrong password. An admin password reset lifts a lockout.
- **Rate limits** (fixed window per client IP, 429 + `Retry-After`): `POST /api/auth/login` and
  `POST /api/auth/password` 10/min, sharing one bucket (both are password oracles);
  `POST /api/auth/refresh` and `POST /api/auth/logout` 30/min. The partition key is the connection's remote IP. Behind
  a reverse proxy this needs `ForwardedHeaders` with a trusted-proxy list - Phase 11. `X-Forwarded-For` is never
  read directly. The limits are configuration-bound (`RateLimit:LoginPermitsPerMinute` = 10,
  `RateLimit:RefreshPermitsPerMinute` = 30, validated 1-100000) only so that the E2E environment can raise them (its
  browsers, workers and helpers share one IP; `scripts/e2e-stack.mjs` sets 1000/3000). **Production must keep the
  defaults**; do not set these variables in a deployed environment.
- **Per-request token re-validation**: on every authenticated request (JwtBearer `OnTokenValidated`) the user is
  looked up in SQL. The token is rejected (401) unless the user exists, is active, is not deleted and still holds
  exactly the role in the token. Deactivation, deletion and demotion therefore apply immediately, and authorization
  comes from SQL rather than a stale claim. One primary-key lookup per request; the same lookup also reads
  `MustChangePassword`.
- **Password change** (`POST /api/auth/password`): verifies the current password, applies the policy, revokes every
  other refresh family of the user and keeps the caller's own family (identified by the refresh cookie). It lives under
  `/api/auth` so the browser sends the `Path=/api/auth` cookie. A wrong current password counts towards the same
  lockout as failed logins (5 → 15 minutes); while locked out even the right current password is refused (same 400,
  nothing verified). Rate limited with login (above).
- **Deactivate / reset**: both revoke all of the user's refresh tokens. A reset also sets `mustChangePassword`, so the
  target's still-unexpired access tokens are blocked (403 password-change-required) on their very next request.
- **Token responses**: login and refresh responses carry `Cache-Control: no-store` and `Pragma: no-cache` (as do the
  temporary-password responses). A failed refresh (401) deletes the dead refresh cookie with the same attributes it
  was set with.
- **Errors**: 401 bodies are generic; JwtBearer error details are disabled. Only the authentication challenge (missing,
  invalid, expired or stale access token) carries `WWW-Authenticate: Bearer`; credential failures on the anonymous
  token endpoints (wrong login, failed refresh) are plain 401 ProblemDetails without it.

## Must-change-password enforcement

- Source of truth is SQL: the per-request `ActiveUserCheck` projection reads `MustChangePassword` and `OnTokenValidated`
  puts it on the principal as a **server-added** claim `must_change_password = "true"` (issuer `enterprise-rag:server`).
  Any claim of that name inside the token is stripped first, so a token can neither impose nor lift the block.
- `PasswordChangeRequiredRequirement` is part of the **default**, **fallback** and **AdminOnly** policies (the fallback
  policy alone does not apply to endpoints that carry their own authorization metadata). Its handler succeeds unless
  the user must change their password and the endpoint is not marked `[AllowWhilePasswordChangeRequired]`.
- Allowlist (exactly two, asserted by a test that walks every endpoint): `POST /api/auth/password`, `GET /api/me`.
  Anonymous endpoints (login, refresh, logout, health, `/`) never evaluate policies, so logout and refresh stay
  reachable.
- The denial is **403** ProblemDetails with `type: https://enterprise-rag.local/problems/password-change-required`
  (written by a custom `IAuthorizationMiddlewareResultHandler`), distinguishable from an ordinary 403
  (`.../problems/forbidden`). If a must-change user also lacks a role (e.g. a non-admin on an admin route), the
  password-change problem is returned first.
- After `POST /api/auth/password` clears the flag, the **same** access token works on the next request (no re-login).
  An admin reset sets the flag, blocking the target's existing access tokens immediately.
- Any new authorization policy must add the requirement; the endpoint-walk test fails otherwise.

## Authorization

- **Authenticated by default**: a fallback policy requires an authenticated user for every endpoint; only login,
  refresh, logout, `/health/*` and `/` opt out with `AllowAnonymous`.
- **AdminOnly**: policy `AdminOnly` (role claim `Admin`) on `/api/admin/*`; the handlers re-check admin
  (`RequireAdmin`) as defense in depth. Non-admins get 403.
- **Knowledge-base access** goes through `IAccessPolicy.RequireKnowledgeBaseAsync(kbId, minimumRole)` in every KB
  handler. Roles are ordered Viewer < Editor < Owner.
  - Missing, soft-deleted and non-member knowledge bases all produce the identical **404** (no existence oracle).
  - A member below the required role gets **403**.
  - There is **no admin back door**: a global Admin has no implicit access to knowledge bases and gets 404 like any
    non-member. Admins manage users, not content.
  - Removing a member, deleting a KB or demoting takes effect on the very next request with the same token, because
    membership is read from SQL on each call. `PermissionVersion` increments on every membership change.
- **Request-shape errors before resource resolution**: model binding and FluentValidation (400, 428) run before the
  resource is looked up, so malformed requests get 400 regardless of whether the target exists or is visible. This
  avoids using validation errors as an existence oracle in the other direction and keeps rulings deterministic.
- **Audit log**: append-only `AuditLogs` (updates/deletes rejected by an EF interceptor). Written for login
  success/failure, refresh, reuse detection, logout, password change/reset, user create/deactivate and all KB and
  membership changes. Entries carry actor, target and small details, never passwords, tokens or hashes. Written
  through a separate context after the handler's own save.
- **Optimistic concurrency**: knowledge bases carry a rowversion exposed as a strong ETag; `PUT` requires `If-Match`
  (428 missing, 400 malformed, 412 stale). The supplied version is compared with the loaded one before saving, so a
  stale `If-Match` is a 412 even when the body changes nothing. Only a failed client precondition is a 412: losing a
  race on an endpoint without `If-Match` (e.g. two concurrent membership changes) is a 409.

## Known trade-offs and deferred items

- I5 (Phase 11): the failed-login counter is a read-modify-write, so concurrent wrong passwords can lose increments
  (lost update) and allow slightly more than 5 attempts per lockout window. Deliberately NOT fixed with a rowversion on
  `User`: a concurrency failure there would make conflicting requests distinguishable (an existence/timing oracle). The
  fix is an atomic `UPDATE ... SET FailedLoginCount = FailedLoginCount + 1 ... OUTPUT` in Infrastructure. The per-IP
  rate limit bounds the damage meanwhile.
- M5: audit entries are written after the handler's commit (own context). If the audit write fails, the request
  returns 500 although the change was committed. For `POST /api/admin/users` the one-time temporary password is then
  lost; recovery is an admin password reset of the created user.
- M8: a user-initiated password change revokes the other sessions' refresh tokens, but their already-issued access
  tokens stay valid until expiry (at most 15 minutes). (An admin reset blocks them immediately via must-change.)
- M11: Serilog request logging records the request path including the query string, so user-directory search terms
  (`/api/users/directory?query=`) appear in logs. To be trimmed with the logging review (Phase 10/11).
- The proxy-aware client IP for rate limiting is Phase 11; until then all clients behind one proxy share a bucket.
  Requests with a null remote IP share an "unknown" bucket.
- The per-request SQL check also runs on anonymous endpoints if a (stale) Bearer header is sent, and a database
  outage inside `OnTokenValidated` most likely yields 500 instead of 503.
- 401 responses for credential failures (wrong login, failed refresh) do not carry `WWW-Authenticate` (they are not
  bearer challenges); only the JwtBearer challenge does.
- 499 (client closed the request) is logged at Debug and has no body: nobody is left to read it.
- Lockout/failed-login: the wrong-password path saves once more than strictly needed (a minor timing difference);
  `maxAttempts <= 0` is not guarded in the domain (options range-validate it to 1-100).
- Email validation is FluentValidation's `EmailAddress` (weak); the seed email is not format-validated.
- Seed: no longer gates on pending migrations; it tolerates only SQL errors 207/208 (schema missing or behind) and
  connectivity failures, otherwise an empty Users table without valid Seed config fails startup. Every unique-key
  violation is reported as 409; `SuccessRehashNeeded` (hash upgrade) is not surfaced.
- `ChangeTracker.Clear()` on conflict detaches all tracked entities (documented on `IAppDbContext.SaveChangesAsync`);
  callers must re-query.
- JWT signing-key rotation is not supported (single key; rotating it signs everyone out).
- Audit entries commit in their own context/connection; they are not part of the handler's transaction.
- Membership list shows every member's name and email to every member including Viewers (product decision to confirm).
- Audit append-only is enforced in EF only; DB-level enforcement is planned for Phase 10.
- Not implemented yet: email verification/password reset by email, MFA, external login, token revocation list for
  access tokens (mitigated by the 15 min lifetime plus the per-request SQL check), HTTPS/HSTS and proxy handling
  (Phase 11).
